# Спецификация проекта: Hotel Management Automation

## 1. Введение

**Цель проекта:**  
Автоматизация управления бронированиями для гостиницы с использованием интеграции с внешней PMS и управления через Telegram-бот. Проект направлен на упрощение работы менеджеров, создание прозрачного аудита действий и обеспечение отказоустойчивости критичных операций.

**Основные задачи:**
- Автоматическая и ручная синхронизация бронирований с PMS.
- Управление бронированиями, клиентами, комнатами через удобный Telegram-бот.
- Хранение истории изменений и проведение аудита действий пользователей.
- Настройка гибкого контроля доступа (ABAC) для разных ролей через политики в YML.
- Отказоустойчивая отправка уведомлений с сохранением информации о задержках доставки.
- **Новый функционал:** Возможность запроса через Telegram, какие номера свободны на указанную дату, для указанного числа гостей и на заданное количество дней.

---

## 2. Архитектура системы

### 2.1. Общий обзор

Система разделена на два основных сервиса:

- **TelegramBotService:**
  - Обработка входящих Telegram-сообщений и команд.
  - Формирование интерактивных сообщений (с инлайн-кнопками, меню).
  - Управление сессиями и маршрутизация команд к BackendService.
  - Представление данных, полученных от BackendService.

- **BackendService:**
  - Реализация всей бизнес-логики: интеграция с PMS, синхронизация бронирований, CRUD-операции для бронирований, клиентов и комнат.
  - Обработка нового функционала – поиск свободных номеров по заданным параметрам (дата, количество гостей, продолжительность пребывания).
  - Управление настройками, аудит и контроль доступа (ABAC).
  - Отправка системных уведомлений через NotificationService (часть BackendService).

### 2.2. Взаимодействие между сервисами

- TelegramBotService обращается к BackendService через REST API для:
  - Получения данных (информация по бронированиям, клиентам, комнатам, дашборд и т.д.).
  - Выполнения действий (создание/обновление бронирований, ручной запуск синхронизации, запрос свободных номеров).
- BackendService обеспечивает целостность и безопасность данных, применяя JWT-аутентификацию, ABAC (с политиками в YML через SpEL) и глобальное логирование/аудит.

## 3. Описание доменов и REST API

### 3.1. Синхронизация

- **POST /api/sync**  
  **Функционал:**
  - Запуск синхронизации бронирований с внешней PMS (периодически, раз в 5 минут, и по требованию через REST вызов).
  - Обработка ошибок (с использованием Spring Retry) и обновление статуса синхронизации.
  - Запись времени последнего опроса.
  - Уведомление при сбоях синхронизации через NotificationService.

### 3.2. Бронирования

- **GET /api/booking/{id}**
  - Получение детальной информации о бронировании, включая данные о клиенте, комнате, датах, статусе, сумме, заметках и истории изменений.

- **POST /api/booking**
  - Создание нового бронирования (ручное создание через Telegram-бот, если необходимо).

- **PATCH /api/booking/{id}**
  - Обновление бронирования: подтверждение предоплаты, перемещение (в т.ч. массовое), отмена, добавление или редактирование заметок.
  - Фиксация изменений в таблице истории бронирований (Booking_History).

- **GET /api/bookings?date=...&prepaid=...**
  - Поиск бронирований по параметрам: дате заезда или создания, наличию предоплаты, источнику бронирования и т.д.

### 3.3. Клиенты

- **GET /api/client/{id}**
  - Получение полной информации о клиенте (ФИО, телефон, email, адрес, даты создания/обновления, заметки).

- **GET /api/clients?name=...**
  - Поиск клиентов по имени (с использованием fuzzy-поиска по вычисляемому полю full_name).

- **PATCH /api/client/{id}**
  - Редактирование данных клиента, включая обновление заметок.

### 3.4. Комнаты

- **GET /api/room/{id}**
  - Получение информации о конкретной комнате (номер, этаж, характеристики, заметки).

- **GET /api/rooms?number=...**
  - Поиск комнат по номеру или другим параметрам.

- **PATCH /api/room/{id}**
  - Редактирование данных комнаты (обновление заметок и другой информации).

### 3.5. Поиск свободных номеров (Новый функционал)

- **GET /api/rooms/available?fromDate=YYYY-MM-DD&numDays=N&guests=M**  
  **Функционал:**
  - По заданной дате (`fromDate`), на указанное количество дней (`numDays`) и для указанного числа гостей (`guests`) возвращаются все доступные номера.
  - Система анализирует текущие бронирования, статус каждой комнаты и её вместимость (из таблицы Rooms) для формирования списка свободных номеров.
  - Результаты возвращаются в виде списка доступных комнат с основными характеристиками (номер, этаж, тип, вместимость, и дополнительные данные).

### 3.6. Дашборд

- **GET /api/dashboard?date=YYYY-MM-DD**
  - Получение сводной статистики за выбранный день:
    - Заезды, выезды, текущие проживающие.
    - Новые бронирования, бронирования без предоплаты (с разбивкой по статусу напоминаний).
    - Непрочитанные системные уведомления.
    - Время последней синхронизации.

### 3.7. Уведомления

- **GET /api/notifications/unread**
  - Получение списка непрочитанных уведомлений.

- **POST /api/notifications/read**
  - Отметка уведомлений как прочитанных.

### 3.8. Настройки

- **GET /api/settings**
  - Получение текущих системных настроек (на основе YML-файла).

- **PATCH /api/settings**
  - Обновление настроек (изменение параметров, запись изменений в YML, с последующей перезагрузкой настроек).
  - При ошибках обновления настроек производится уведомление администратора.

### 3.9. Аудит

- **GET /api/audit?objectType=...&objectId=...** (опционально)
  - Получение истории изменений для заданного объекта (бронирование, клиент, комната).

## 4. База данных

### 4.1. Основные таблицы

#### Clients
- **Поля:**
  - `id` – уникальный идентификатор.
  - `first_name`, `last_name`, `middle_name` – части ФИО.
  - `phone` – номер телефона.
  - `email` – адрес электронной почты.
  - `full_name` – вычисляемое поле (объединение first_name, last_name, middle_name) для поддержки fuzzy-поиска.
  - `notes` – текстовое поле с заметками, прикреплёнными к клиенту.
- **Индексация:**
  - GIN-индекс на поле `full_name` с использованием расширения [pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html).
  - B-tree индексы для `phone` и `email` (с использованием lower(email) для регистронезависимого поиска).

#### Bookings
- **Поля:**
  - `id` – уникальный идентификатор.
  - `client_id` – внешний ключ, ссылающийся на таблицу Clients.
  - `checkin_date` – дата заезда.
  - `checkout_date` – дата выезда.
  - Статус бронирования (например, без предоплаты, предоплачено, отменено, проживает).
  - `source` – источник бронирования (например, Booking.com, ручное).
  - `cost` – полная стоимость бронирования.
  - `notes` – текстовое поле с заметками, прикреплёнными к бронированию.
- **Индексация:**
  - Индексы для полей `checkin_date` и `checkout_date`.

#### Booking_History
- **Поля:**
  - `id`
  - `booking_id` – внешний ключ на бронирование.
  - Поля для хранения информации об изменениях: старое значение, новое значение, изменённое поле, время изменения.
- **Назначение:**
  - Отслеживание истории изменений каждого бронирования.

#### Rooms
- **Поля:**
  - `id`
  - Номер комнаты.
  - Этаж.
  - Характеристики:
    - Наличие вида на море,
    - Сторона балкона,
    - Тип комнаты,
    - Максимальное количество взрослых,
    - Рекомендации по размещению.
  - Вместимость – максимальное число гостей, которое может принять комната.
  - `notes` – текстовое поле с заметками по комнате.
- **Индексация:**
  - Индекс по номеру комнаты.

#### Audit_Log
- **Поля:**
  - `id`
  - `timestamp` – время действия.
  - `platform` – платформа (например, telegram, web).
  - `user_id` – идентификатор пользователя (например, Telegram chat_id или внутренний ID для веб).
  - `user_name`, `user_nick` – имя и ник.
  - `user_agent` – строка user agent (если применимо для веб-запросов).
  - `action` – тип совершённого действия (например, create_booking, cancel_booking).
  - `object_type` – тип объекта (booking, client, room).
  - `object_id` – идентификатор объекта.
  - `details` – дополнительная информация (например, изменения в значениях) в формате JSON.

#### Settings
- **Поля:**
  - Хранение глобальных настроек (например, параметры интеграции с PMS, интервалы синхронизации, конфигурация ABAC) хранятся в YML-файле, но здесь можно вести резервную копию или историю изменений.

#### Sync_Status
- **Поля:**
  - `id`
  - `last_sync_at` – время последней синхронизации.
  - `status` – статус (успех, ошибка, в процессе).
  - `duration` – длительность синхронизации.
  - `details` – подробности или описание ошибки.

#### Notifications
- **Поля:**
  - `id` – уникальный идентификатор уведомления.
  - `channel` – тип канала отправки (например, telegram).
  - `message` – текст уведомления.
  - `status` – статус уведомления (например, QUEUED, SENT, FAILED).
  - `retry_count` – количество попыток отправки.
  - `created_at` – время создания уведомления.
  - `scheduled_at` – время, когда уведомление должно было быть отправлено (для отображения задержки).
  - `last_attempt_at` – время последней попытки отправки.
  - `error_details` – текст с деталями ошибки, если уведомление не было отправлено.
- **Назначение:**
  - Уведомления сохраняются в базе до попытки отправки.
  - Фоновый процесс NotificationService (в составе BackendService) обрабатывает их, осуществляет отправку через соответствующий канал, обновляет статус и фиксирует задержки.

## 5. Безопасность

- **Коммуникации:** Все REST-вызовы между сервисами и внешний обмен (с PMS, Telegram API) осуществляются через HTTPS.
- **Аутентификация:**
  - Используем JWT для аутентификации пользователей и сервисов.
  - Валидация токенов на стороне BackendService.
- **Контроль доступа:**
  - Применяем ABAC с политиками, заданными в YML-файле и интерпретируемыми через SpEL.
  - Проверки выполняются в бизнес-логике и через Spring AOP.
- **Хранение секретов:** Конфиденциальные данные (пароли, ключи, JWT-секреты) хранятся вне кода (переменные окружения или специализированные системы).
- **Валидация входных данных:** Использование Bean Validation для проверки всех входящих параметров.

---

## 6. Обработка ошибок и fallback-механизмы

- **Вызовы к внешним системам (PMS):**
  - Применяем Spring Retry для повторных попыток при временных сбоях.
  - При исчерпании попыток фиксируем ошибку, обновляем Sync_Status и отправляем уведомление через NotificationService.

- **Глобальный обработчик исключений:**
  - Использование @ControllerAdvice для перехвата исключений и возврата структурированного JSON с описанием ошибки (включая traceId).

- **Обработка ошибок в TelegramBotService:**
  - В случае ошибки обращения к BackendService пользователь получает дружелюбное сообщение о временной недоступности сервиса.
  - Возможны повторные попытки запроса.

- **Логирование:**
  - Все критичные ошибки логируются и, при необходимости, инициируется оповещение в специальный Telegram-канал для администраторов.

## 7. Контейнеризация и развертывание

- **Docker:**
  - Каждый сервис (TelegramBotService и BackendService) упаковывается в отдельный Docker-образ.
- **Docker Compose:**
  - Используется для локальной разработки и тестирования, позволяя поднять весь стек (сервисы, PostgreSQL и другие компоненты).
- **CI/CD:**
  - GitHub Actions для автоматизации сборки, тестирования, создания Docker-образов и развертывания на тестовое/staging-окружение (с ручным подтверждением для production).
- **Миграции БД:**
  - Управление схемой базы данных реализовано с помощью Flyway (версионированные скрипты миграций).

---

## 8. Мониторинг и оповещения

- **Health-check:**
  - Использование Spring Boot Actuator для мониторинга состояния сервисов через эндпоинты.
- **Логирование:**
  - Централизованный сбор логов через стек EFK (Elasticsearch, Fluentd, Kibana).
- **Мониторинг метрик:**
  - При необходимости интеграция с Prometheus и Grafana.
- **Оповещения:**
  - NotificationService отправляет системные уведомления при критичных событиях (сбои синхронизации, ошибки настроек, недостаток места в БД и т.д.).

---

## 9. Тестирование

- **Юнит-тесты:**
  - Покрытие бизнес-логики с использованием JUnit, Mockito и прочих инструментов.
- **Интеграционные тесты:**
  - Тестирование REST API через Spring Boot Test.
  - Использование mock/stub-сервера (например, WireMock) для эмуляции PMS.
- **End-to-End тестирование:**
  - Имитация сценариев через TelegramBotService, проверка корректной работы цепочки запросов и ответов.

## 10. Заключение

Проект построен на модульной архитектуре, разделённой на TelegramBotService (интерфейс для пользователей) и BackendService (бизнес-логика, интеграция с PMS, управление уведомлениями, аудит и настройками). Принятые решения по безопасности, обработке ошибок, отказоустойчивости и мониторингу обеспечивают надёжность системы. Новый функционал по поиску свободных номеров позволяет пользователям (через Telegram) задать дату, количество дней и число гостей для получения информации о доступных номерах, что делает систему более удобной и функциональной.
