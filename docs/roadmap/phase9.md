## Этап 9. Аудит

**Цель:** обеспечить централизованное логирование всех действий пользователей.

---

### 1. Аудит (Audit)

- **Таблицы и сущности**  
  - `audit_actor` с полями: id, платформа, user_id, user_name, user_nick, user_agent, ip_address, created_at  
  - `audit_log` с полями: id, timestamp, actor_id → `audit_actor`, action, object_type, object_id, details (JSONB)  

- **Контекст пользователя**  
  - Использовать `AuditContextHolder` на основе `ThreadLocal` для хранения текущего актёра в рамках HTTP-запроса или обработки Telegram-сообщения  
  - При входе каждого запроса или обновления бота заполнять контекст активным пользователем (chat_id, username, платформа, ip, user_agent)  

- **Аннотация для методов**  
  - Создать `@AuditableAction`, принимающую параметры `action` и `objectType`  
  - Помечать ею все сервисные методы, где нужно фиксировать операцию  

- **Аспект аудита**  
  - В `AuditAspect` перехватывать вызовы методов с `@AuditableAction`  
  - До или после выполнения сохранять в `audit_log` запись с привязанным `actor_id`, именем действия, типом объекта, идентификатором объекта (из аргументов или результата) и дополнительными данными в JSON  

- **Проверка**  
  - Unit-тесты для `AuditAspect`, мокая `AuditLogRepository`, убеждаться, что запись создаётся с правильными данными  
  - Интеграционные тесты HTTP и Telegram, проверяющие появление записей в `audit_log` после выполнения команд
